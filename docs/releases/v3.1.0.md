# v3.1.0 upgrade and release guide

The release packages the review-safety and decision-correctness fixes merged after v3.0.0. It is a minor version: action paths, input and output names, and defaults stay the same, but automatic approval is stricter and the bundled Pi runtime moves to a new major line, so callers who opted into approval or supply their own Pi binary should read the upgrade notes.

## What changed

| Pull request | Change |
|---|---|
| #165 | The reviewer's `grep` and `find` results drop every `.git` entry, and all inspection results redact authorisation headers and GitHub tokens, so a job token persisted by `actions/checkout` cannot reach the model provider. The security engine resolves its gateway from the frozen `OPENAI_API_URL`/`OPENAI_API_MODEL` variables. PR titles, bodies, patches, and confirmation snippets are redacted with the full detector set. Token detectors need a left boundary (no more `disk-cache-…` "OpenAI key" findings) and `Bearer` no longer merges two diff lines. |
| #166 | The security confirmation pass no longer trusts a `confirmed` label written by the reasoning model; only deterministic scanner occurrences may skip it. The confirmer receives the diff hunk covering the claimed line instead of the first 5,000 characters of the patch. Model text in security inline comments and the sticky summary is escaped Markdown. |
| #167 | The Pi runtime moves from the deprecated `@mariozechner/pi-coding-agent@0.73.1` to `@earendil-works/pi-coding-agent@1.5.2` (clearing GHSA-jfgx-wxx8-mp94 and every runtime audit finding) and runs with `--no-approve` and `--no-mcp`. |
| #168 | The Octokit adapter keeps review state, commit, and body, so re-runs recognise their own block on the head. A complete run with nothing blocking dismisses the action's own earlier `CHANGES_REQUESTED`. Categories match case-insensitively and through common synonyms. Auto-approval is refused while a changed file went unreviewed or a category had to be bucketed. The test-probe title filter applies only to `low` findings, and the inline buffer lives in the per-job runner temp directory. |

The full list is in [CHANGELOG.md](../../CHANGELOG.md#310--20112026).

## Upgrade from v3.0.0

```yaml
- uses: niko0xdev/action-code-review/pr-review@v3.1.0
- uses: niko0xdev/action-code-review/pr-content@v3.1.0
```

These entries illustrate action references; supply the required inputs and permissions in the caller workflow.

- **Checkout credentials.** Set `persist-credentials: false` on `actions/checkout`, as the documented workflows now do, so the job token never sits in `.git/config` while the reviewer inspects the repository. The `.git` result filter is defence in depth, not a reason to keep the token on disk.
- **Stricter auto-approval.** `auto-approve-when-resolved` stays opt-in (default `false`). When enabled, approval is now also refused while any changed file kept by the configured filters went unreviewed: cut by `max-files`, without a patch from GitHub, or under a default-ignored path such as `dist/`, `build/`, `vendor/`, or a lockfile. List such paths in `exclude-patterns` to accept them explicitly. Approval is also refused when a finding's unknown category had to be lowered to `low`.
- **Stale blocks are lifted.** A complete run with no blocking finding dismisses the action's own earlier `CHANGES_REQUESTED` review. The existing `pull-requests: write` permission covers this; no new permission is needed. Reviews by people or other workflows are never dismissed.
- **Custom Pi binaries.** The bundled runtime is Pi 1.5.2 and is called with `--no-approve` and `--no-mcp`. A custom `pi-binary-path`, or a preinstalled `pi` used by the security fallback, must be Pi 1.x: Pi 0.x rejects those options and the review fails. Runners that use the bundled install need no change.
- **Unchanged limitation.** `security-profile: lite|balanced|deep` still requires a compatible Piolium adapter and reports an incomplete run without one, as in v3.0.0.

New report fields remain additive under schema version 1. SARIF schema version remains 2.1.0; its tool version is 3.1.0.

## Tags and verification

- `v3.1.0` identifies the exact release commit and is not moved after publication.
- `v3.1` is a new alias that tracks compatible releases in the 3.1 minor line.
- `v3` moves to the v3.1.0 release commit and keeps tracking compatible releases in major version 3.
- `v3.0` and `v3.0.0` keep their target (`204c8d3`). Callers pinned to them stay on v3.0.0 until they change the reference.

Before publishing, run strict TypeScript (`pnpm typecheck`), Biome (`pnpm lint`), coverage tests (`pnpm test:coverage`), the actual pinned-runtime boundary suite (`pnpm test:runtime` after `npm ci --prefix pr-review/pi-runtime --ignore-scripts`), both bundle builds (`pnpm build`, with no diff against the committed `pr-*/dist`), a semantic bundle check (the bundles carry `3.1.0` and the new boundary code), and a startup smoke run (`node pr-review/dist/index.js`). Merge the release preparation only after its checks pass, then create the exact tag and the aliases at that merge revision, and publish release notes with the source revision and distribution checksums.

After publication, a held real PR must consume `niko0xdev/action-code-review/pr-review@v3.1.0` and `niko0xdev/action-code-review/pr-content@v3.1.0`, rather than local paths or main. Verify from the workflow logs that the resolved Action revision is the release commit, and check the actual PR state: the posted findings, the blocking review on a blocking finding, its dismissal after a clean re-run on a new head, and the incomplete-run safeguard. Test the `v3.1` and `v3` aliases as well. Label controlled-provider publication tests and actual live-provider assessments separately. Close the canary without merging its fixture or workflow changes, and record the observed run identifiers and the final outcome in the GitHub release notes.

## Dependency audit triage – 20/11/2026

The root production audit is unchanged from v3.0.0: six high, twelve moderate, and three low advisories, all through `@actions/core`/`@actions/github` (`undici@5.29.0`, `@fastify/busboy`, and the `@octokit/request`, `@octokit/request-error`, and `@octokit/plugin-paginate-rest` ReDoS entries). No root dependency changed in this release, so the non-reachability assessment in the [v3.0.0 guide](v3.0.0.md#dependency-audit-triage--18112026) still applies unchanged: the shipped entrypoints do not use the WebSocket, multipart, custom-TLS, or TLS-renegotiation paths, the GitHub client uses its own Node agents rather than the Undici dispatcher, and provider transport uses Node fetch or the separately locked runtime.

The locked Pi runtime audit (`npm audit --omit=dev` in `pr-review/pi-runtime`) now reports no vulnerabilities. The v3.0.0 runtime entries (`proxy-agent` → `basic-ftp`, `extract-zip`, and the Pi advisories) left with the move to `@earendil-works/pi-coding-agent@1.5.2`.

The root findings remain deferred by demonstrated default-path non-reachability, not fixed. Review by 25/11/2026, or before changing transport dependencies, enabling tool downloads with `PI_OFFLINE=0`, forwarding proxy configuration, or substituting a custom runtime.

## History rewrite – 20/11/2026

The repository history was rewritten after the v3.1.0 publication, for two
reasons: commit messages still carried third-party tool co-author trailers, and
the authorship was split across two accounts. The rewrite was a message and
identity filter, not a content filter.

| Change | Effect |
|---|---|
| Third-party co-author trailers removed from commit messages | The tool accounts no longer appear in the repository's contributor list. |
| Authors and committers consolidated under `niko0xdev` | Every commit on `main` now has one author. |
| Every commit and branch re-pointed at its rewritten equivalent | Commit identifiers changed; trees did not. |
| `v3`, `v3.0`, `v3.0.0`, `v3.1`, and `v3.1.0` re-pointed at their rewritten equivalents | The release line keeps the same published content. |
| `v2.0.0` and `v2.0.1` left untouched | The v2 exact tags keep their original targets, as documented above. |

What this means for a consumer:

- The code at every published tag is byte-identical to before; only the
  commit identifiers changed. A workflow pinned to `@v3.1.0` or `@v3` runs the
  same action code.
- A local clone must be re-pointed: `git fetch origin && git reset --hard
  origin/main`, or `git clone` again. A plain `git pull` can fail with a
  divergent-history error.
- A fork that shares the old history keeps it; push the rewritten history to
  overwrite it.

The rewrite was verified before it was published: the tree identifier of
`main` is unchanged (`0277fca7d75e74a3b8d89413c86a3c3910d5682b`), the commit
count is unchanged at 199, and every branch kept the tree it had before.

## Rollback

Consumers can pin either action to the exact `v3.0.0` tag while investigating a regression. That restores the v3.0.0 approval rules and the Pi 0.73.1 runtime, without the security fixes listed above. Preserve the exact v3.1.0 tag as evidence; do not rewrite it. If the published distribution is defective, document the issue on the release, move `v3.1` and `v3` only to a verified compatible replacement, and publish a new patch version.

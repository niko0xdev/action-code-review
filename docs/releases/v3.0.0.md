# v3.0.0 upgrade and release guide

The release packages the audited implementation and the changes since v2.0.1. It uses a new major version because default approval and review scope have changed. The earlier development milestone labelled 3.0.0 in the working changelog was not the published release described here.

## Upgrade from v2.0.1

Both entrypoints remain available:

```yaml
- uses: niko0xdev/action-code-review/pr-review@v3.0.0
- uses: niko0xdev/action-code-review/pr-content@v3.0.0
```

These entries illustrate action references; supply the required inputs and permissions in the caller workflow.

`auto-approve-when-resolved` now defaults to `false`. To request automatic approval explicitly, set it to `'true'`. Approval still requires a complete assessment, at least one earlier AI-authored thread, all such threads resolved, no dropped severity findings, and sufficient configured permission. Opting in does not restore unconditional approval.

The default exclusions are now `*.md,*.txt`, so JSON/YAML manifests and workflows are reviewed too. Lockfiles stay excluded unless `AI_REVIEW_INCLUDE_LOCKFILES=true`. A caller that intentionally retains the old file selection can set `exclude-patterns: '*.md,*.txt,*.json,*.yml,*.yaml'` explicitly.

Malformed, incomplete, clipped, or failed analysis cannot approve. Incomplete reviews fail the check by default; `AI_REVIEW_FAIL_ON_INCOMPLETE=false` only changes failure signalling, not the approval guard. Runtime guard and confirmation requirements are described in the [remediation matrix](../audit-remediation-2026-11-17.md). The guard is an application boundary, not an operating-system sandbox.

Existing action paths and input/output names remain available. New report fields are additive under schema version 1. SARIF schema version remains 2.1.0; its tool version follows the package release.

## Tags and verification

- `v3.0.0` identifies the exact release commit and is not moved after publication.
- `v3.0` tracks compatible releases in the 3.0 minor line.
- `v3` tracks compatible releases in major version 3.
- Existing v2 exact tags keep their original targets. No v2 alias is redirected to v3.

Before publishing, run strict TypeScript, Biome, coverage tests, the actual pinned-runtime boundary suite, both bundle builds, semantic bundle checks, and startup smoke checks. Merge the release preparation only after its checks pass, then verify post-merge CI. Create the exact tag and compatible aliases at that verified merge revision, and publish release notes with the source revision and distribution checksums.

After publication, a held real PR must consume `niko0xdev/action-code-review/pr-review@v3.0.0` and `niko0xdev/action-code-review/pr-content@v3.0.0`, rather than local paths or main. Verify the resolved Action revision from workflow logs, actual PR state, generated content, and incomplete/blocking safeguards. Test the compatible aliases as well. Controlled-provider publication tests and actual live-provider assessments must be labelled separately. Close the canary without merging its fixture or workflow changes. The GitHub release notes record the observed run identifiers and final outcome.

## Dependency audit triage – 18/11/2026

The native audits are not clean: root production audit reports six high, twelve moderate, and three low advisories; the independent locked runtime audit reports eight high and two moderate package entries, including propagated dependency-chain entries. Neither reports a critical finding. No dependency version or lockfile was changed during release preparation.

| Reported dependency paths | Reachability assessment for the default Action execution |
|---|---|
| Root `@actions/http-client` → `undici@5.29.0` → `@fastify/busboy@2.1.1` | The reported WebSocket, multipart, custom-TLS callback, and TLS-renegotiation paths are not called by the shipped entrypoints. The GitHub client uses `HttpClient.getAgent()` (Node/tunnel agents), rather than its separate Undici dispatcher. The Action does not request OIDC tokens through `core.getIDToken()`. Provider transport uses Node fetch or the separately locked runtime. |
| Runtime `proxy-agent` → `pac-proxy-agent` → `get-uri` → `basic-ftp` | The relevant runtime provider imports this chain for configured Bedrock proxies. `buildPiEnv()` does not forward HTTP/PAC proxy variables; the security fallback forwards only an explicitly selected provider credential. The vulnerable FTP listing parser is not reached in those isolated executions. |
| Runtime `extract-zip@2.0.1` | The installed runtime uses it for Windows search-tool downloads. The Action sets `PI_OFFLINE=1` by default, so missing tools cannot enter the downloader. Linux CI installs search tools from the host package manager. Installation uses `npm ci --ignore-scripts`; neither the bundle build nor the runtime boundary tests call ZIP extraction. |

Evidence comes from `src/harness/pi.ts` (`buildPiEnv`), `src/security/engines/pi-security-engine.ts`, the committed runtime lockfile, and installed sources for `@actions/github@5.1.1` internal proxy handling, `@actions/http-client@2.2.3`, and the pinned runtime's `utils/tools-manager.js` and Bedrock provider. The runtime's active Undici installation is 7.30.1, distinct from the root package's 5.29.0.

Primary advisory examples: [Undici custom-TLS handling](https://github.com/advisories/GHSA-2m5v-pch6-74hx), [multipart parsing](https://github.com/advisories/GHSA-x8mw-p69m-v3mx), [FTP directory parsing](https://github.com/advisories/GHSA-c475-qrg2-pj4r), and [ZIP symlink extraction](https://github.com/advisories/GHSA-7pqw-9j4j-h8q3). These findings are deferred by demonstrated default-path non-reachability, not removed or marked fixed. Review by 25/11/2026, or before changing transport dependencies, enabling tool downloads with `PI_OFFLINE=0`, forwarding proxy configuration, or substituting a custom runtime. Custom configurations require a fresh assessment.

## Rollback

Consumers can pin either action to the exact previously validated `v2.0.1` tag while investigating a regression, with the earlier approval defaults and missing later security fixes understood. Preserve the exact v3.0.0 tag as evidence; do not rewrite it. If a published distribution is defective, document the issue on the release, move compatible v3 aliases only to a verified compatible replacement, and publish a new patch version. A v2 revision must not be presented as a v3-compatible replacement.

# feat: rich summary + hard 2-state decision (APPROVE / REQUEST_CHANGES)

## Background

Current PR summary after V2 review is too sparse:
```
# 🤖 AI Code Review
**Reviewed files:** 1
**Total issues found:** 0
```

This branch makes the summary **rich + actionable** AND introduces **hard 2-state decision**:
- 0 findings, or only `low`-severity findings → submit review with `event=APPROVE`
- Any `medium`/`high`/`critical` finding → submit review with `event=REQUEST_CHANGES` + inline comments

### T2 — Hard 2-state decision in `v2/src/github/review.ts`

Modify `publishReview` so the review submission uses `event=APPROVE` when there are no blocking findings, else `REQUEST_CHANGES`:

```ts
// After dedupe against existingComments:
const hasBlockingFinding = findings.some((f) => f.severity !== 'low');

if (findings.length > 0) {
  const event: ReviewPayload['event'] = hasBlockingFinding ? 'REQUEST_CHANGES' : 'COMMENT';
  // ... existing batch comment logic uses 'event' instead of payload.event
}

// Always post summary
await octokit.rest.issues.createComment({ ... });

// SEPARATELY: if 0 findings after filter OR only-low findings, submit APPROVE review
if (findings.length === 0 || !hasBlockingFinding) {
  try {
    await octokit.rest.pulls.createReview({
      owner, repo, pull_number: prNumber,
      commit_id: headSha,
      event: 'APPROVE',
      body: '✅ AI Code Review: no blocking issues found. Auto-approving.',
    });
  } catch (error) {
    console.warn(`Approve review failed: ${error instanceof Error ? error.message : String(error)}`);
  }
}
```

Important:
- `APPROVE` review MUST be a separate `createReview` call (cannot combine `event: APPROVE` with inline comments per GitHub API).
- The existing batch-comment fallback (`COMMENT` event for non-blocking) stays as-is.
- `REQUEST_CHANGES` review is the existing flow — keep the batch + fallback.

So the new flow:

```
1. Filter findings by existing IDs
2. If findings.length > 0:
     a. If ANY medium/high/critical:
        → createReview(event=REQUEST_CHANGES, inline comments[])
     b. ELSE (all low):
        → createReview(event=COMMENT, inline comments[])  ← already low severity, just note
3. Always: createComment(issue, body=buildSummaryBody(...))
4. If NO blocking findings (zero or all-low):
     → createReview(event=APPROVE, body='Auto-approve...')
```

Notes:
- Step 4 is independent of step 2 — they can both fire (e.g., 2 low findings → step 2 posts COMMENT review, step 4 also posts APPROVE review). That's the right semantic: low issues are informational, merge OK.
- Use `params.blockOnIssues` to gate step 4? NO — keep it always-fire per user spec (hard 2-state, no opt-out for now). Future-proof: could add `AI_REVIEW_AUTO_APPROVE` env var later.
